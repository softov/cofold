A host answers an approval or a question on the handle `run()` gave it, and the run goes on there, as pi and the Claude Agent SDK answer inside the live run.
The request is announced only once the run is recorded waiting for it, and every handle's stream ends with a `run.finished`, so no host has to guess how a run ended.

## What was built

- [`code://packages/agents/src/run/answer.ts`](../../../../packages/agents/src/run/answer.ts) - `liveRuns` (the runs attached in this process), `waitForCommand(ctx, pending)` and `validateCommand(ctx, pending, command)`, moved out of `resume.ts` so `run()` and `resume()` reach the same wait; `TurnContext.accept` is the acceptor while a request is open.
- [`code://packages/agents/src/run/turn.ts`](../../../../packages/agents/src/run/turn.ts) - `pause()` writes the request record and `runs.update(awaiting)` and installs the acceptor *before* publishing `approval.requested` / `input.requested`, then `run.paused` and a `run.finished { awaiting }`; it clears the heartbeat, sets the handle's status to `awaiting` without closing it, and awaits the command. `processCalls` loops the call through `pause` and `applyResolved`, so the rest of the batch keeps its order.
- [`code://packages/agents/src/run/handle.ts`](../../../../packages/agents/src/run/handle.ts) - the handle takes `agentId` and an optional `startSeq`, gained an internal `setStatus`, `steer` while `awaiting` enqueues, and `finish` pushes a `run.finished` into the buffer when the run did not publish one (not stored, not handed to `onEvent`).
- [`code://packages/agents/src/run/run.ts`](../../../../packages/agents/src/run/run.ts), [`code://packages/agents/src/run/abort.ts`](../../../../packages/agents/src/run/abort.ts) - `start()` installs an `onCommand` that reaches `ctx.accept` and joins `liveRuns` for the wait; the run's timeout timer is `unref()`'d, so a host that leaves a paused handle can exit.
- [`code://packages/agents/src/types/run.ts`](../../../../packages/agents/src/types/run.ts) - `RunHandle` says `status()` may read `awaiting` and then `running` again, `events` ends after the `run.finished` that is not `awaiting`, and `outcome` resolves once, at the run's end.
- [`code://packages/papo/src/chat.ts`](../../../../packages/papo/src/chat.ts) - `handleFor` became `recover(sessionId)`: the attached handle when it holds the newest run, else `resume()` (with `steerHeld`) and `attach`, which is the restart case. `attach` folds a `Stop` deferred per pause and `wait` returns it, so `papo say` and the other three `wait` callers still stop at a pause. `cancel` goes through the handle the process holds, whatever its status; `close()` cancels only the handles that are working and leaves an `awaiting` one, which is what makes `papo say` then `papo approve` across two invocations work.
- [`code://examples/agents/pause-resume.ts`](../../../../examples/agents/pause-resume.ts), [`code://examples/agents/ask-user.ts`](../../../../examples/agents/ask-user.ts), the two READMEs - the pause example runs process 1 as a real child process that exits at the pause and process 2 resumes the folder; the question example answers on the handle that is waiting; `packages/agents/README.md` says how a pause is read and answered, and that `resume()` is for a run this process does not hold.

## Departures from the plan

- Task 02 - a command submitted from inside an `onEvent` observer of `approval.requested` is taken, but its `approval.resolved` can be published before the pause's own `run.paused` and `run.finished { awaiting }`, because the observer's `submit` gets a microtask's head start. The strict order holds on the ordinary path and the test asserts it there.
- Task 04 - `recover` passes `afterSeq` (the last event the store holds) to `resume()`, so a resumed handle reads from where the store's events end rather than replaying the pause it is about to answer. Without it a `wait` issued right after `approve` could take the replayed `run.finished { awaiting }` and report a pause the run had already left. `say` was left as it is: its `writer_busy` while the session already waits on a decision is decision CLI-05.4's own rule, and step 3's "`say` submits it there" is met by the harness.
- Task 05 - the child stops at the `run.finished` that carries `awaiting` rather than at `run.paused`, because that is the last event the pause writes and exiting earlier can leave the folder without it. Each process builds its own fake model with the one step it plays (the old example worked only because both "processes" shared one `createFakeModel` object in one process), and the child is handed the temp folder as an argument so both open the same store.
- Not in the plan, and answered by Softov after it was built: [`code://packages/store-file/src/store.test.ts`](../../../../packages/store-file/src/store.test.ts)'s "a session folder copied to another root resumes there" broke under this plan, for two reasons that are both decision 122's - a pause keeps its handle open, so `await first.outcome` never resolves (it resolves once, at the run's end), and the run stays in `liveRuns` while it waits, so a same-process `resume()` is refused `writer_busy`. The test now reads the pause off the events, up to the `run.finished` that carries `awaiting`, and models the second process with a fresh module registry - the pattern [`code://packages/papo/src/chat.test.ts`](../../../../packages/papo/src/chat.test.ts)'s `otherProcess` already uses - which builds its own agent and fake model from what the copied folder holds. The tool is the first process's, so its execution count is shared and the test's point is unchanged: pause, copy the folder to another root, approve from the copy, and the tool runs exactly once.

## Review fixes

Softov's review of this plan found four ways a handle could outlive the run it answers. Each is fixed, and each has a test that was run against the code without the fix and fails there.

- **A stale paused handle wrecked a run another process had resumed.** Process A pauses; process B resumes and approves; then A's `cancel()` or its timeout fires. A used to persist a deny into the run B held, move the record back to `running`, `finishRun(cancelled)` over B's result and release B's claim, so B died `not the writer` if it was still working. `apply` in [`code://packages/agents/src/run/answer.ts`](../../../../packages/agents/src/run/answer.ts) now asks `requests.get` whether the request is still open, and a request answered elsewhere is not written to at all: the handle detaches (`detachRun`) - no resolution, no run update, no `finishRun`, no `releaseWriter` - and ends its own stream with the outcome read back from the store. `storedOutcome` moved from `resume.ts` to [`code://packages/agents/src/run/turn.ts`](../../../../packages/agents/src/run/turn.ts) so both readers share it.
- **`papo cancel` took over a run a live process was writing.** It recovered any `running` record it did not hold, and `resume()` re-claims the lock with the same runId, so the other process's run ended `interrupted` under it. [`code://packages/papo/src/chat.ts`](../../../../packages/papo/src/chat.ts)'s `cancel` now resumes a `running` record only when the writer lock's process is gone, read from `SessionRecord.activeWriterPid` - a new field on [`code://packages/agents/src/types/store.ts`](../../../../packages/agents/src/types/store.ts), filled by [`code://packages/store-file/src/store.ts`](../../../../packages/store-file/src/store.ts)'s `readSession` from the lock's `pid`; a memory store records none, which reads as gone, and `isAlive(pid)` asks with signal 0, `EPERM` counting as alive. An `awaiting` record is recovered as before. The held handle is used only while it still is the newest run.
- **The check above the write could be won between the two.** A second review pass found the same race one step in: `apply` asked whether the request was still open, and another process could answer it between that read and `store.requests.resolve`, whose refusal then took the catch into `finishRun(failed)` over the other process's run. The catch now asks `answered()` again before it fails anything, and a request answered in the gap detaches exactly as the early branch does, rethrowing `not_found` and writing nothing. The case in `run/answer.test.ts` is a store double whose `requests.resolve` lands another process's resolution and then refuses the write; before the fix the submit resolved `undefined` (the plain error's code) and the record read `failed`, and after it the submit rejects `not_found` with the request's resolution, the `awaiting` record and the writer claim all as the other process left them.
- **A pause whose announcement threw left a live acceptor on a finished run.** An emit of `approval.requested`, `run.paused` or `run.finished` that threw left `ctx.accept` and the abort listener installed, so a late `approve` reached `apply` and ran `finishRun` a second time. `pause`'s failure path now drops the wait before it rethrows, and [`code://packages/agents/src/run/handle.ts`](../../../../packages/agents/src/run/handle.ts)'s `submit` refuses `approve`, `deny` and `answer` on a closed handle with `not_running`. Three assertions in `run/resume.test.ts` that pinned the old refusal from such a handle (an unknown run, a cancelled run, and a handle refused `writer_busy`) now read `not_running`, the code the closed handle answers with.
- **A paused run a host closed held its place forever.** With `timeoutMs: 0` (the default) a paused run never left `liveRuns`, so a `resume()` in the same process after `papo`'s `close()` was refused `writer_busy` for good. `RunHandle` gained `detach()`, which `detachRun` answers: the wait, its abort listener, the timeout and this process's entry in `liveRuns` go, nothing is written, the record stays `awaiting` and the handle closes with that outcome. `close()` in [`code://packages/papo/src/chat.ts`](../../../../packages/papo/src/chat.ts) detaches a handle that is `awaiting` and cancels one that is working, so quitting no longer answers the pause.

The tests: [`code://packages/agents/src/run/answer.test.ts`](../../../../packages/agents/src/run/answer.test.ts) is new, one case each for the stale handle (the other process is caught mid-call with a tool it opens by hand, so its claim is held when the stale handle fires and the test shows the record, the resolution and the claim untouched), for the failed announcement (a store double that refuses every write from `run.paused` on; the late `approve` is refused and the request stays open), and for `detach` (the run is refused `writer_busy` while held, and resumable here once detached). [`code://packages/papo/src/chat.test.ts`](../../../../packages/papo/src/chat.test.ts) gained the live-pid case, which also shows a dead pid still being recovered, and the `close()` case, which approves the run after the close and finds the tool ran once.
